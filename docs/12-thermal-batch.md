# 🌡️ الدفعة الحرارية v4 — خفض حرارة الشريحة من داخل الفيرموير

> **التاريخ:** 2026-11-14 | **الحالة:** مبنية ونُشرت على العتاد — الجولة الأولى أحرزت نتيجة مهمة (انظر القسم 5): العطل العشوائي **أُعيد إنتاجه** مع `custom_rx_hooks=1` ⇒ رجعنا للـ baseline المستقر (0)، والدفعة الحرارية بقيت كاملة (السقف اليدوي يعمل بدون hooks)
> **الهدف:** تقليل حرارة TL-WN422G v2 عبر خفض مصدَّري الحرارة الرئيسيين: **قدرة خرج الـ PA** و**كثافة الإرسال (duty)** — تحكم مقيم بالفيرموير نفسه.

---

## 1️⃣ الاكتشاف الحاكم: لا يوجد حساس حرارة

فحص شامل لسورس الفيرموير (`grep -ri 'temp|thermal|therm'`) أكد: **AR9271 لا يعرض ريجستر حرارة مقروءاً وقت التشغيل** — لا يمكن قراءة حرارة الـ die من داخل الشريحة ولا من الدرايفر. لذلك:

- "التحسين الحراري" هنا = **إدارة مصادر الحرارة** (قدرة الإرسال × كثافة الإرسال) لا قياس الحرارة.
- القياس الفعلي للحرارة = خارجي (لمس/كاميرا حرارية) + مؤشرات وسيطة (`tx_window`) عبر أمر thermal.

## 2️⃣ الميزات المنفذة (كلها داخل الـ tick الموجود — بلا إرسال WMI دوري)

### أ) المُحكِّم الحراري (Governor) — يعمل كل 2s داخل `custom_periodic_chores`

| الآلية | الوصف | الافتراضي |
|---|---|---|
| **cap حسب جودة الرابط** (bit0) | متوسط RSSI للنافذة ≥45 → سقف `48` | <35 → سقف `60` (كما هو) | بينهما → ثبات (hysteresis) | **مفعّل** |
| **تراجع الحمل** (bit1) | إذا تجاوز الإرسال 1500 استخدام-rate/2s → إنزال القدرة خطوتين/tick، واسترجاع بطيء عند الهدوء (<100) | **معطّل** (لا يمس سرعة التحميل) |
| **سقف يدوي ثابت** | `cap` من الأمر — يتغلب على القرار التلقائي دائماً | معطل (0xFF) |
| **أرضية أمان** | القدرة لا تهبط تحت المؤشر `20` أبداً (يمنع موت الرابط) | دائم |

- القدرة الفعالة لكل إطار بيانات تُحسب من دالة واحدة `custom_tx_power_effective()` في `if_owl.c` بدل القيمة الخام `custom_tx_power`.
- كل تغيير قرار يُسجَّل في **الصندوق الأسود** (type 5: `backoff<<8 | cap`) لما بعد الوفاة.
- الإشارة الحالية للشريحة **-49dBm** ⇒ الرابط "قوي" ⇒ السقف يهبط 60→48 تلقائياً (خفض ~12 مؤشر ≈ -6dB تقديرياً على خرج الـ PA) **بدون أي أثر عملي على السرعة** بهذه الإشارة.

### ب) أمر WMI جديد: `WMI_CUSTOM_THERMAL_CMDID` (0x2F)

- أمر 12B / رد **28B** (تحت سقف 64B): `mode, cap, backoff, effective, avg_rssi, tx_window, rx_window`.
- `mode`/`cap` بقيمة `0xFF` = استعلام فقط. `flags` = bit0/1 لقلب `custom_rx_hooks` وقت التشغيل.
- الدرايفر: `ath9k_wmi_thermal()` + ملف debugfs **`thermal`** (0600):
  ```bash
  cat $D/thermal              # استعلام حي
  echo mode 0 > $D/thermal    # تعطيل المحكم (سلوك قديم تماماً)
  echo cap 60 > $D/thermal    # رفع السقف اليدوي لِـ 60
  echo mode 3 > $D/thermal    # تفعيل تراجع الحمل أيضاً
  echo hooks 0 > $D/thermal   # عزل مسار RX (أداة Bisect بدون إعادة بناء!)
  ```

### ج) `custom_rx_hooks` — قابل للقلب وقت التشغيل (وإرجع = 0 افتراضياً)

- **درس الجولة الأولى:** اشترطتُ أول مرة قلبه لـ 1 (بسبب حل العطل #4)، لكن العتاد أعاد إنتاج توقيع الـ wedge فوراً (بعد ~2 رد مخصص) ⇒ **العطل العشوائي لم يُحسم بعد** — قيمة 0 هي الـ baseline المستقر الموثق.
- القلب **أصبح أمراً وقت التشغيل** (`echo hooks 0|1 > thermal`) — أداة Bisect أفضل من الأصل: يمكن اختبار "الخطافات مفعّلة" لحظياً بدون إعادة بناء ونشر، ومع فحص `wmi_diag`/`custom_ping` مباشرة بعده.
- مع `hooks=0`: الـ tick والـ governor التلقائي يتعطلان (السقف اليدوي `cap` يعمل طبيعياً — انظر القسم 2أ). تفعيل السقف الذكي بالـ RSSI مؤجل لحسم الـ wedge.

## 5️⃣ نتيجة الجولة الأولى على العتاد (19:44) — درس مهم

- النشر نجح: FW 51,148B إقلاع سليم، HTC 33 credits، `thermal` ظهر في debugfs، الشريحة أعادت الاتصال بالشبكة تلقائياً.
- **تسلسل الوفاة:** `custom_ping` نجح (diag سليم: 877 rx_cmds / allocfail=0) ← `rate_usage` نجح ← **`rssi_hist` timeout ← كل الأوامر المخصصة بعده timeout** — نفس توقيع العطل التاريخي "يموت بعد ~2 رد".
- مع hooks=1 + شريحة غير مرتبطة (لا ترافيك) الخطافات تكاد لا تعمل ⇒ الوفاة على الأرجح في **مسار الردود نفسه** وليس في الخطافات — بالضبط ما `probe-reply-capacity.sh` مبني لتشخيصه (pool الردود/credits).
- **القرار:** رجوع `custom_rx_hooks=0` (baseline المستقر) + إعادة بناء (تم 19:56) — والدفعة الحرارية بقيت: **السقف اليدوي `cap` لا يعتمد على الـ hooks إطلاقاً**، فتقليل الحرارة متاح فوراً حتى قبل حسم العطل.

## 5b) خطة التحقق (الجولة الثانية) — ✅ **منفذة وحُسمت في جلسة docs/13**

- **العطل العشوائي المفتوح ("يموت بعد ~2 رد مخصص") اتحسم بالدليل وإصلح** — السبب: حزم WMI control بطول 64B-تماماً على السلك تعلق USB controller (usbmon: الرد يصل ثم EP3 يبث EOVERFLOW ×1401 وEP4 يتوقف عن ACK). rssi_hist (64B مع trailer) وchan_survey وnetflow كانت فوق الحد. الإصلاحات الثلاثة + cap الـ trailer في `_HTC_SendMsg` — التفاصيل الكاملة والاختبار النهائي في **docs/13**.
- الاختبار الكامل النهائي: **50 PASS / صفر WMI timeouts / 3 FAIL موثقة** (ack_timeout readback لا يحتفظ — قيد منصة مؤجل؛ nf غير معايرة على راديو idle — صادق).
- **thermal مثبت حياً**: `cap 48` → `effective=48/63` فوراً ✓ و`cap 255` → uncapped ✓ (دلالة 255 كانت unreachable واتصلحت). `avg_rssi` يبقى 0 مع hooks=0 (العينات تعتمد الـ RX hook).

```bash
sudo /home/mohamed/Projects/ath9k-fw-build/deploy.sh
sudo /home/mohamed/Projects/ath9k-fw-build/test-all.sh   # الأقسام 15 — بوابة قبول v3 (rssi_hist) + كل الأوامر

# القسم الحراري (16) — السقف اليدوي (لا يحتاج hooks):
D=$(ls -d /sys/kernel/debug/ieee80211/phy*/ath9k_htc | head -1)
sudo cat "$D/thermal"                      # mode/cap/backoff/effective/avg_rssi
echo cap 48 | sudo tee "$D/thermal"        # سقف يدوي 48 — effective يهبط فوراً 60→48
sleep 2 && sudo cat "$D/thermal"           # تأكيد effective=48 (تقليل حرارة PA نشط)
echo cap 255 | sudo tee "$D/thermal"       # إزالة السقف اليدوي (255 = uncapped)

# اختبار الـ hooks وقت التشغيل (Bisect — يفعّل الخطافات + governor):
echo hooks 1 | sudo tee "$D/thermal"
sudo cat "$D/thermal" && sudo cat "$D/rssi_hist"   # لو ردّا: الخطافات بريئة
sudo cat "$D/custom_ping" 2>/dev/null; echo 777 | sudo tee "$D/custom_ping"
sudo cat "$D/wmi_diag"                     # لو الردود ماتت: cmd_timeouts يزيد
```

- **معيار النجاح:** الأقسام الـ 15 تستجيب + `effective` يهبط إلى 48 بعد ثوانٍ من الاتصال + `avg_rssi` منطقي (~40-50 عندك).
- **قياس الحرارة:** لمس/كاميرا حرارية قبل وبعد دقائق تشغيل — المتوقع انخفاض ملموس في حرارة منطقة الهوائي/الـ PA مع بقاء RSSI كما هو.
- **لو wedged:** `sudo reset-target.sh` ثم فك فيزيائي إن لزم؛ **التراجع الكامل:** `sudo rollback.sh`.
- بعد التحقق الناجح: حدّث `patches/` (snapshot v3+v4) وحدّث docs/08-09.

## 6️⃣ قرارات تصميمية موثقة

- **تراجع الحمل معطل افتراضياً:** تحميل مستمر ~4Mbps يولّد ~540 استخدام/2s (تحت عتبة 1500)، لكن تفعيله افتراضياً كان سيعاقب أي تنزيل طويل — فعّله بـ `mode 3` إن أردت أقصى تبريد أثناء الأحمال.
- **عتبات RSSI 45/35:** قابلة للمعايرة بعد أول قراءة حية لـ `avg_rssi` — إن ثبت أن إشارتك تهبط تحت 45 غالباً، ارفع `CUSTOM_TH_CAP_WEAK/STRONG` أو استخدم `cap` اليدوي.
- **إطارات Beacon/Mgmt تبقى على 60:** كثافتها مهملة حرارياً؛ التعديل مسار البيانات فقط (نقطة `ah_setupTxDesc` في `if_owl.c`).
